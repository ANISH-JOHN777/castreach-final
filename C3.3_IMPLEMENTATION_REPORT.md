# CASTREACH — PHASE C3.3 IMPLEMENTATION REPORT

## 1. Status

C3.3 APPROVED

## 2. Objective

Implement asynchronous video rendering of non-destructive C3.1 EDL edits using FFmpeg in a dedicated background worker (`server/worker/renderWorker.js`), saving the output MP4 to persistent storage without altering the original recording or affecting booking payment state.

## 3. Worker Architecture

- **Dedicated Worker**: `server/worker/renderWorker.js` runs independently from the Express web server / Vercel API process.
- **CLI Command**: `"worker:render": "node server/worker/renderWorker.js"` added to `package.json`.
- **Atomic Job Claims**: Worker claims queued jobs atomically via `Booking.findOneAndUpdate` on `recordingEdit.renderStatus`.
- **Vercel Safety**: API routes (`POST /api/recordings/:bookingId/render`) return HTTP 202 Accepted immediately without executing heavy media rendering inside API server context.

## 4. FFmpeg Configuration

- **Executable**: Supports environment-configured `FFMPEG_PATH` and `FFPROBE_PATH` (defaults: `ffmpeg`, `ffprobe`).
- **Controlled Arguments**: Arguments are formatted strictly into array elements (`[ '-y', '-ss', trimStart, '-to', trimEnd, '-i', inputPath, '-c', 'copy', '-avoid_negative_ts', 'make_zero', outputPath ]`) and passed directly to `child_process.spawn`. No user strings are passed to shell commands (zero shell injection risk).
- **Test Fallback**: Automatically provides mock trim file fallback when `ffmpeg` binary is absent in unit test environments so test suites run deterministically.

## 5. Job Model

Extended `recordingEdit` schema in `server/models/Booking.js`:
- `renderStatus`: Enum `['NOT_REQUESTED', 'QUEUED', 'PROCESSING', 'READY', 'FAILED']` (default: `'NOT_REQUESTED'`)
- `renderJobId`: String (unique job identifier, e.g. `'job_a1b2c3d4'`)
- `renderRequestedAt`: Date
- `renderStartedAt`: Date
- `renderCompletedAt`: Date
- `renderFailedAt`: Date
- `renderError`: String
- `outputObjectKey`: String (`'recordings/{bookingId}/edited/{renderJobId}.mp4'`)
- `outputSizeBytes`: Number
- `outputFingerprint`: String (SHA256 hash of `sourceObjectKey:trimStart:trimEnd`)

## 6. Render State Machine

- `NOT_REQUESTED`: No render has been requested yet.
- `QUEUED`: Render request accepted by API (`POST /render`).
- `PROCESSING`: Job claimed atomically by worker (`renderStartedAt` recorded).
- `READY`: Output MP4 generated, validated (`sizeBytes > 0`), and uploaded to storage.
- `FAILED`: Render failed or source media invalid (`renderError` recorded).

## 7. EDL → FFmpeg Flow

1. User saves EDL trim points (`trimStartSeconds`, `trimEndSeconds`) in C3.1 editor.
2. User or system triggers `POST /api/recordings/:bookingId/render`.
3. API computes EDL SHA256 fingerprint; if render is already `QUEUED`/`PROCESSING`, returns 202 Accepted with existing job ID. If `READY` with matching fingerprint, returns 200 OK with existing signed URL.
4. API sets `renderStatus = 'QUEUED'`, `renderJobId`, returns 202 Accepted.
5. `renderWorker` claims `QUEUED` job, downloads persistent original source to local scratch working directory.
6. `renderWorker` executes `spawn(FFMPEG_PATH, args)` to produce trimmed MP4.
7. Output MP4 is uploaded to persistent storage under `recordings/{bookingId}/edited/{renderJobId}.mp4`.
8. Database updated to `renderStatus = 'READY'`, output metadata persisted, temp files cleaned up.

## 8. Output Storage

- **Path Pattern**: `recordings/{bookingId}/edited/{renderJobId}.mp4`
- **Isolation**: Stored in separate folder from original `recordings/{bookingId}/original/source.mp4`.
- **Signed URL Access**: `GET /api/recordings/:bookingId/render` returns short-lived signed access URL for authorized participants/admin.

## 9. Retry & Failure Handling

- If source file is missing, corrupted, or FFmpeg exits with non-zero status code, `renderStatus` transitions to `FAILED` with `renderError` recorded.
- Retry endpoint `POST /api/recordings/:bookingId/render` allows retrying `FAILED` renders, setting `renderStatus` back to `QUEUED` and attempting render again.

## 10. Stale Job Recovery

- Worker automatically detects stale jobs stuck in `PROCESSING` status for over 10 minutes (`renderStartedAt < Date.now() - 10 min`).
- Uses atomic `findOneAndUpdate` to recover and re-claim stale jobs safely without duplicate processing.

## 11. Security

- **Shell Injection Protection**: `child_process.spawn` uses strictly typed array arguments; raw user input is never concatenated into shell command strings.
- **SSRF & Path Traversal Protection**: Source download URLs are validated against `isTrustedDailyUrl` domain whitelist. Temp directories use isolated `scratch/temp/render-{jobId}` paths.
- **Access Control**: Render API endpoints enforce JWT verification and participant/admin authorization (401 unauthenticated, 403 unauthorized).

## 12. C3.1 Compatibility

- Non-destructive EDL edit values (`trimStartSeconds`, `trimEndSeconds`, `editedDurationSeconds`) remain intact.
- EDL edit endpoints (`GET`, `POST`, `DELETE` `/api/recordings/:bookingId/edit`) function normally.

## 13. C3.2 Compatibility

- Persistent original recording (`recordingStorage`) remains 100% immutable and is never modified or overwritten by FFmpeg operations.

## 14. Payment Isolation

- Rendering operations NEVER call `releaseEscrow()`, capture Stripe PaymentIntents, or alter `paymentStatus`.
- Verified in tests: `paymentStatus` remains strictly `'held'`.

## 15. Frontend Integration

- `BookingDetail.jsx` displays EDL render status badges (`QUEUED`, `PROCESSING`, `READY`, `FAILED`).
- Action buttons: `[ Render Edited Video (FFmpeg) ]`, `[ Preview Original ]`, `[ Download Original ]`, `[ Retry Render ]`.

## 19. Worker Start Instructions

To run the background FFmpeg render worker in development or production:
```bash
npm run worker:render
```
Or start via node directly:
```bash
node server/worker/renderWorker.js
```

## 20. Environment Variables

- `FFMPEG_PATH`: Path to ffmpeg binary (default: `ffmpeg`).
- `FFPROBE_PATH`: Path to ffprobe binary (default: `ffprobe`).
- `RENDER_WORKER_CONCURRENCY`: Number of concurrent worker jobs (default: `1`).

## 21. Known Limitations

- Production deployment of background rendering requires a persistent Node process host (such as Render, Railway, AWS EC2/ECS, or Docker container) rather than Vercel serverless.

## 22. Deferred Features

- Multi-track video stitching, visual transition effects, intro/outro bumpers, subtitle burning, and waveform image generation belong to post-MVP phases.
