## 2. Objective

Move the original Daily cloud recording from temporary Daily-managed storage into application-controlled persistent object storage (`recordingStorage`), keeping the original recording immutable for future C3.3 FFmpeg rendering workers.

## 3. Existing Storage Infrastructure

Inspected environment variables and existing backend dependencies. Found `@aws-sdk/client-s3` in `package.json` with AWS S3 / Cloudflare R2 / S3-compatible configuration support (`AWS_S3_BUCKET`, `AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_S3_ENDPOINT`). Constructed a unified storage abstraction service (`server/services/storage.js`) that operates over S3/R2 when credentials are provided, or seamlessly falls back to stream-piped local object storage (`scratch/storage/recordings/`) for dev/test without external dependencies.

## 4. Storage Provider

Implemented a clean storage abstraction service (`server/services/storage.js`). It supports:
- AWS S3 / Cloudflare R2 / MinIO via `@aws-sdk/client-s3` (`Upload`, `GetObjectCommand`, `PutObjectCommand`).
- Local filesystem fallback (`scratch/storage/recordings/`) with stream piping.
- Short-lived presigned/signed access URLs (1-hour expiration).
- Deterministic storage key pattern: `recordings/{bookingId}/original/source.mp4`.

## 5. Persistent Recording Architecture

- **Storage Key Pattern**: `recordings/{bookingId}/original/source.mp4`
- **Daily Webhook (`recording.ready-to-download`)**: When received and verified, backend streams recording directly from Daily URL into persistent storage.
- **File Verification**: HTTP 200 check, non-zero content-length check, content-type (`video/mp4`) verification. Zero-byte downloads are rejected with status `FAILED`.
- **Immutability**: The original recording is marked with provider `s3`/`r2`/`local` and objectKey, never overwritten by any EDL editing operations.

## 6. Database Changes

Extended `server/models/Booking.js` with `recordingStorage`:
- `provider`: String (e.g. `'s3'`, `'r2'`, `'local'`)
- `objectKey`: String (e.g. `'recordings/6ab75.../original/source.mp4'`)
- `status`: String, enum: `['NOT_STORED', 'STORING', 'READY', 'FAILED']`, default: `'NOT_STORED'`
- `contentType`: String (default: `'video/mp4'`)
- `sizeBytes`: Number (default: `0`)
- `storedAt`: Date
- `error`: String

All existing fields (`recordingUrl`, `recordingReady`, `recordingStatus`, `recordingDuration`, `dailyRoomUrl`, `recordingEdit`) remain intact.

## 7. Daily Webhook Integration

Updated `server/routes/webhooksDaily.js` (`recording.ready-to-download` event):
1. HMAC signature verification via `verifyDailySignature`.
2. Event idempotency via `ProcessedWebhookEvent`.
3. Validates booking presence and status (`CONFIRMED`/`COMPLETED`).
4. Invokes `storageService.mirrorRecording(booking._id, dailyRecordingUrl)` using streaming.
5. Persists `booking.recordingStorage` with status `READY` (or `FAILED` if download/upload stream breaks).
6. Returns deterministic HTTP 200 response without unhandled promise rejections.

## 8. Streaming / Large File Handling

- Used Node stream piping (`stream.Readable.fromWeb(res.body)` to `fs.createWriteStream` or `@aws-sdk/lib-storage` `Upload` stream).
- Avoids loading large multi-gigabyte recording files into Node `Buffer`/RAM.

## 9. Idempotency

- Uses existing `ProcessedWebhookEvent` model to deduplicate `recording.ready-to-download` events.
- If duplicate webhook events arrive, `ProcessedWebhookEvent.findOne({ eventId })` returns HTTP 200 immediately.
- If storage is already `READY`, re-triggering webhook or retry skips duplicate upload.

## 10. Failure Handling

- If HTTP fetch fails, returns non-200, or encounters network error, `booking.recordingStorage.status` is set to `FAILED` with `error` message recorded.
- Recording lifecycle status (`recordingStatus`), `booking.status`, and `paymentStatus` (`'held'`) remain completely untouched.

## 11. Retry Strategy

- Implemented `POST /api/recordings/:bookingId/retry-storage`.
- Requires JWT authentication and participant/admin authorization.
- Uses Daily `recordingUrl` stored on `booking` as source.
- Validates trusted source URL via strict SSRF domain check (`isTrustedDailyUrl`).
- Idempotently retries stream transfer to persistent storage and updates `recordingStorage.status` to `READY` upon success.

## 12. Access Control

- Storage URLs are never publicly exposed.
- API endpoint `GET /api/recordings/:bookingId/storage-url` enforces authorization:
  - Host (`booking.hostId`): Allowed (200, returns signed access URL).
  - Guest (`booking.guestId`): Allowed (200, returns signed access URL).
  - Admin (`user.role === 'admin'`): Allowed (200, returns signed access URL).
  - Unauthenticated user: Returns 401 Unauthorized.
  - Unrelated authenticated user: Returns 403 Forbidden.

## 13. Security

- **SSRF Protection**: `isTrustedDailyUrl` validates source host against allowed domain whitelist (`daily.co`, `daily-recordings.s3.amazonaws.com`, etc.). Rejects arbitrary external hosts or user-supplied URLs.
- **Path Traversal Protection**: Storage keys strictly format using Mongo `ObjectId` (`recordings/${bookingId}/original/source.mp4`).
- **Credential Security**: No S3 / storage credentials exposed to client side or included in API responses.

## 14. C3.1 Compatibility

- EDL endpoints (`GET`, `POST`, `DELETE` `/api/recordings/:bookingId/edit`) operate normally.
