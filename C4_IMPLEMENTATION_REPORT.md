# CASTREACH — PHASE C4 IMPLEMENTATION REPORT
## PRODUCTION-GRADE POST-MEETING RECORDING EXPERIENCE

---

### 1. OBJECTIVE
The primary objective of **Phase C4** is to deliver a production-grade, intuitive, and secure post-meeting recording experience for Hosts, Guests, and Administrators. After a podcast recording session ends, participants must have clear visual status, access control, and interaction workflows for both the **Immutable Original Recording** and the **Derived Edited Video (FFmpeg Rendered)**.

### 4. RECORDING LIFECYCLE UX
The UI strictly separates the two backend state machines:
- **Original Recording Lifecycle (`recordingStatus`)**:
  - `NOT_STARTED` / `RECORDING` / `PROCESSING` / `READY` / `FAILED`
- **Edited Video Rendering Lifecycle (`recordingEdit.renderStatus`)**:
  - `NOT_REQUESTED` / `QUEUED` / `PROCESSING` / `READY` / `FAILED`

---

### 5. ORIGINAL RECORDING FLOW
- Status badge visually highlights `Ready`, `Processing...`, or `Failed`.
- Displays session duration (formatted `MM:SS` or `HH:MM:SS`), recorded timestamp, and object storage mirror status.
- Provides **Preview Original** (opens `VideoPreviewModal` using signed storage URL) and **Download Original** (opens signed access link in new window).
- If persistent storage copy fails, provides an inline **Retry Copy** button triggering `POST /api/recordings/:bookingId/retry-storage`.

---

### 6. EDITED RECORDING FLOW
- Status badge displays `Not Rendered`, `Queued`, `Rendering...`, `Ready`, or `Failed`.
- Shows saved C3.1 Edit Decision List (EDL) trim boundaries (`trimStartSeconds → trimEndSeconds`) and active edited duration.
- Actions provided:
  - **Set Trim Range / Edit EDL**: Opens `RecordingEditorModal`.
  - **Render Recording**: Triggers `POST /api/recordings/:bookingId/render` (returns HTTP 202 Accepted).
  - **Preview Edited**: (When `renderStatus === 'READY'`) Opens `VideoPreviewModal` with signed output stream URL.
  - **Download Edited**: (When `renderStatus === 'READY'`) Downloads rendered MP4 via signed output URL.
  - **Retry**: (When `renderStatus === 'FAILED'`) Re-queues job via `POST /api/recordings/:bookingId/render/retry`.

---

### 7. PREVIEW ARCHITECTURE
- Video streams are accessed exclusively via short-lived signed storage URLs generated by `storageService.getSignedStorageUrl` or `storageService.getSignedOutputUrl`.
- Video streams are never sent as raw Base64 JSON strings or loaded completely into JavaScript RAM.

---

### 8. DOWNLOAD ARCHITECTURE
- Clicking "Download Original" or "Download Edited" calls the backend API endpoint (`GET /api/recordings/:bookingId/storage-url` or `GET /api/recordings/:bookingId/render-url`).
- Authenticated participants receive a signed URL and are redirected directly to the storage provider download stream.
- Public storage bucket credentials and secret keys are never exposed in frontend HTTP payloads.

---

### 9. NOTIFICATION BEHAVIOR
- **Original Recording Ready**: Sent via Daily webhook handler to Host and Guest upon initial recording upload.
- **Edited Recording Ready**: Sent via `renderWorker.js` upon FFmpeg completion:
  - Title: `"Edited Recording Ready"`
  - Body: `"Your edited CastReach recording is ready to view."`
  - Link: `/bookings/:bookingId`
- **Edited Recording Failed**: Sent via `renderWorker.js` upon render failure:
  - Title: `"Edited Recording Failed"`
  - Body: `"The edited recording could not be generated."`
  - Link: `/bookings/:bookingId`

---

### 10. AUTHORIZATION & SECURITY (IDOR / SSRF)
- Every recording route enforces strict token authentication (`verifyToken`) and participant check (`[booking.host, booking.guest].includes(req.user.id) || req.user.role === 'admin'`).
- Unauthenticated requests return HTTP 401 Unauthorized.
- Requests by unrelated users return HTTP 403 Forbidden.
- External URLs provided by users are never fed into FFmpeg or storage mirror commands. All input object keys are read strictly from DB booking metadata.

---

### 11. PAYMENT ISOLATION
- Recording operations (viewing, downloading, editing, rendering, retrying) **NEVER** alter `paymentStatus` (remains `'held'`).
- Functions `releaseEscrow()`, `capturePayment()`, and `refundPayment()` are strictly isolated to booking completion/cancellation workflows and are never triggered by recording UI interactions.

---

### 12. BOOKING-STATE ISOLATION
- Recording operations **NEVER** alter `booking.status` (remains `'confirmed'`).
- Host confirmation, guest confirmation, and slot availability remain untouched during video preview, EDL saving, or background rendering.
